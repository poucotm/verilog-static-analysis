## 세션 시작 규칙 (가장 먼저 적용)

### 안내 박스
세션의 첫 메시지에 top 모듈이 없으면, 먼저 `python .claude/skills/verilog-review/scripts/strip_comments.py --spec analysis-spec.md`를 실행해 출력의 `스펙 Top:` 줄을 확인한다 (스펙 원본은 열지 않는다). 그다음 첫 응답은 **아래 `<!-- 안내 시작 -->`과 `<!-- 안내 끝 -->` 사이의 줄뿐**이다. 첫 메시지가 인사나 다른 질문이어도 같다.
- 박스의 `│ <TOP 안내>` 줄은 아래 "TOP 안내" 두 가지 중 하나로 바꿔 쓴다.
- 예외: 첫 메시지가 top 없이 분석 시작을 요청하고(예: `분석을 시작해줘`) `스펙 Top`이 있으면, 박스 대신 버전 줄을 쓰고 그 top으로 사전 확인에 들어간다.

### TOP 안내
`스펙 Top:` 줄에서 모듈 이름 하나를 읽는다 (예: `- top 은 sauvage` → `sauvage`). `없음`이거나 이름이 둘 이상·모호하면 "없음"으로 본다.
- 스펙 Top이 있을 때 (`<이름>`에 그 이름):
```
│ - `analysis-spec.md`에 top이 `<이름>`으로 지정되어 있습니다. 맞으면 "분석을 시작해줘"라고 말씀해 주세요.
│   다른 top으로 하려면: `top 은 <모듈> 로 분석을 시작해줘`
```
- 스펙 Top이 없을 때:
```
│ - 준비되면 top 모듈 이름과 함께 "분석을 시작해줘"라고 말씀해 주세요.
│   예: `top 은 sauvage 로 분석을 시작해줘`  (`analysis-spec.md`의 `## Top`에 적어 두면 이름 없이 시작할 수 있습니다)
```

### 그 밖의 시작 규칙
- 박스 안 버전 줄의 버전과 날짜는 아래 "룰 버전" 절의 값과 같아야 한다.
- **소스 폴더 기본값은 `source`다.** 사용자가 소스 폴더를 말하지 않으면 `source`를 소스 폴더로 쓰고, 사전 확인(`verilog-review` 3.0)에서 "소스 폴더: source (기본값)"으로 보여준다.
- 첫 메시지에 top이 있어 바로 분석에 들어가는 경우에도, 첫 응답의 첫 줄에 버전 줄을 쓴다.
- **top 결정 순서**: 사용자가 말한 top → `analysis-spec.md`의 스펙 Top. 사용자가 top 없이 `분석을 시작해줘`라고 하면 스펙 Top으로 시작한다. 둘 다 없으면 시작하지 않고 top 이름을 지정해 분석을 시작해 달라고 안내한다 (TOP 안내의 "없을 때" 줄).
- 사용자가 말한 top과 스펙 Top이 다르면 사용자 top을 쓰고, 사전 확인 메시지에 `스펙 Top(<이름>)과 다름`을 적는다.
- 첫 메시지에 소스 폴더만 있고 top이 없으면 소스 폴더는 확인해 주고, 스펙 Top이 있으면 그 top으로 시작할지 묻고 없으면 top을 요청한다.
- 소스 폴더와 top이 정해지기 전에는 Verilog 파일을 읽거나 분석을 시작하지 않는다.
- 지정한 폴더(기본값 `source` 포함)가 프로젝트 폴더 밖이거나 존재하지 않으면 분석하지 말고 소스 폴더를 다시 요청한다.
- 지정한 폴더에 top 모듈 정의가 없으면 분석하지 말고, 폴더에서 찾은 최상위 후보 모듈(어디서도 인스턴스되지 않는 모듈)을 보여주고 다시 요청한다.
- 소스 폴더와 top이 정해지면 이 세션 동안 그대로 사용한다. 사용자가 바꾸라고 할 때만 바꾼다.
- 소스 폴더와 top이 정해지면 본격 분석 전에 **사전 확인**을 한다 (`verilog-review` 3.0).
  - 모듈 정의와 인스턴스만 빠르게 훑어 **분석 / 그레이박스 / 블랙박스 / 미사용** 모듈과 파일, **참고 스펙(`analysis-spec.md`, 주석 밖 내용)**을 보여주고, **사용자가 맞다고 답할 때까지 분석을 시작하지 않는다.** 이 확인은 생략하지 않는다.
  - 구성이 맞다는 답을 받으면 바로 분석을 시작한다. 분석이 끝나면 **묻지 않고 항상 PDF 보고서까지 만든다** (`/verilog-report`).

## 룰 버전
- 버전: v0.8.15
- 날짜: 2026-11-19
- 구성: CLAUDE.md, verilog-review skill, verilog-report skill

버전 줄은 `Verilog RTL 정적 분석 룰 v<버전> (<날짜>)` 형식으로 출력한다. 위 "세션 시작 규칙"과 "정보 요청"에서 쓴다.

## 정보 요청
사용자가 "버전", "정보", "룰 정보", "도움말", "사용법" 등을 물으면, 세션 중 언제든 다른 작업 없이 아래를 출력한다.
1. 버전 줄 (`Verilog RTL 정적 분석 룰 v<버전> (<날짜>)`)
2. 버전, 날짜, 구성 ("룰 버전" 절 그대로)
3. 사용법 요약
   - 분석 시작: `top은 <모듈>로 분석을 시작해줘`. `analysis-spec.md`의 `## Top`에 top이 있으면 `분석을 시작해줘`만으로 시작 (소스 폴더는 기본 `source`, 다른 폴더면 `소스 폴더 <경로>, top은 <모듈>로 …`. 시작 전에 분석·그레이박스·블랙박스 구성을 보여주고 맞는지 확인받는다. 분석이 끝나면 PDF 보고서까지 만든다)
   - 보고서만 다시 만들기: `verilog-report로 PDF 보고서 만들어줘`
   - 수정 후 재분석: `/clear`로 새 세션을 시작한 뒤 `top은 <모듈>로 분석을 시작해줘`
4. 현재 세션의 소스 폴더와 top (소스 폴더를 말하지 않았으면 "source (기본값)", top이 정해지지 않았으면 "미지정")

## 프로젝트 정보
- 설계 대상: [예: UART 컨트롤러, 영상 처리 파이프라인]
- top 모듈: 세션 시작 시 사용자가 지정하거나 `analysis-spec.md`의 `## Top`에 적는다
- 타깃: [FPGA 벤더/디바이스 또는 ASIC 공정]
- 언어: Verilog-2001 / SystemVerilog [사용하는 쪽만 남기기]

## 분석 대상 범위
- 분석 대상 Verilog 소스는 **세션 시작 시 지정한 소스 폴더 하위의 파일만**이다 (`*.v`, `*.sv`, `*.vh`, `*.svh`). 소스 폴더는 프로젝트 폴더 하위여야 한다.
- 소스 폴더 밖의 파일은 include 경로에 있어도 분석에 쓰지 않는다. (프로젝트 폴더의 `analysis-spec.md`는 스펙으로 참고한다)
- 인스턴스로 사용되지만 소스 폴더 안에 정의가 없는 모듈은 **블랙박스**로 취급한다. 세부 규칙은 `verilog-review` skill을 따른다.
- 소스 폴더 아래 `graybox` 폴더 안에 정의된 모듈은 **그레이박스**로 취급한다. 다른 모듈의 신호 흐름을 분석하는 근거로만 읽고, 그 모듈 자체의 문제는 분석하지 않는다. 세부 규칙은 `verilog-review` skill 5.5장을 따른다.

## 디렉터리 구조
- `<소스 폴더>/` : 분석 대상 RTL. 기본값은 `source/`, 세션 시작 시 다른 경로를 지정할 수 있다 (예: `rtl/uart`, `src/`)
- `analysis-spec.md` : 분석용 스펙 (선택, 프로젝트 폴더 바로 아래 이 파일 하나). Top, 입력·출력 조건, 의도된 동작, 성능·전력 목표, 요청 사항을 적는다.
  - **`<!-- -->` 주석 안의 내용(작성 안내와 예시)은 읽지도 해석하지도 않는다.** 스펙은 주석을 지운 사본(`reports/.nocomment/analysis-spec.md`)으로만 읽고 원본은 열지 않는다. 주석 밖에 내용이 없으면 스펙이 없는 것으로 본다.
  - 분석 전 사전 확인(`verilog-review` 3.0)에서 스펙 항목 수를 분석 구성과 함께 보여주고 확인받는다.
- `reports/` : 분석 결과(`<top>_review_<YYYYMMDD>.md`)와 보고서(`pdf/<top>_report_<YYYYMMDD>.md/.pdf`)
  - `reports/.nocomment/` : 소스 폴더와 `analysis-spec.md`에서 주석을 지운 분석용 사본. 세션 시작과 분석마다 새로 만든다.
- `reports/`는 프로젝트 폴더 바로 아래에 둔다. 없으면 필요할 때 만든다.

## 도구 사용
- **분석은 코드를 읽어서만 한다 (정적 분석).** 시뮬레이터(iverilog, verilator 등), lint, 합성 도구(yosys 등), 정형 검증 도구는 설치되어 있어도 실행하지 않는다. 테스트벤치나 assertion 파일도 만들지 않는다.
- 분석 중 쓰는 것은 파일 읽기와 검색(Read, Grep, Glob 등)뿐이다. 예외로 세 명령은 실행한다: 주석을 지운 분석용 사본 만들기(`.claude/skills/verilog-review/scripts/strip_comments.py`, 소스와 `analysis-spec.md` 원본은 읽기만 하고 사본을 `reports/.nocomment/`에 만든다. 세션 시작 때는 `--spec`만), 분석 시작 시각 기록(`date -u +%Y-%m-%dT%H:%M:%SZ`), `.claude/skills/verilog-review/scripts/session_usage.py` (소스 파일 줄 수를 세고 세션 로그를 읽기만 한다).
- PDF 변환에만 pandoc + xelatex를 쓴다. 없으면 설치할지, Markdown 보고서로 마칠지 사용자에게 묻는다 (`verilog-report` 5.1). 묻기 전에는 설치하지 않는다.
- 실행 환경이 Windows일 수 있다. 셸 명령은 Bash(Git Bash) 기준으로 쓰고, 경로는 `/` 구분자를 사용한다.

## 일반 원칙
- 응답과 리포트는 한국어로 작성한다.
- **지정한 소스 폴더 안의 파일**은 사용자가 명시적으로 요청하기 전에는 수정·이동·삭제하지 않는다. 포맷팅, 리네이밍도 포함. 소스 폴더 안에 새 파일도 만들지 않는다.
- 수정 요청을 받으면 변경 범위를 먼저 말하고, 변경 후 영향받는 신호 흐름을 정적으로 다시 확인해 결과를 보고한다.
- 분석 결과와 보고서는 `reports/`에만 만든다.
- 코드에 대한 주장에는 `파일:라인`을 붙인다.
- 스펙(`analysis-spec.md`)과 코드가 다르면 어느 쪽이 맞는지 단정하지 말고 차이를 보고한다.

## Verilog 분석
- 코드 리뷰, 잠재 버그 탐색, 신호 흐름 분석 요청은 `verilog-review` skill의 절차를 따른다. 직접 실행: `/verilog-review`
- 분석의 초점은 lint나 단순 신호 누락이 아니라, 신호 간 관계와 흐름을 따라가야 보이는 잠재 문제(출력 결과 이상, 멈춤·교착, 잘못된 state, 이벤트 유실·중복, 리셋 의존 오동작, 버퍼 넘침, 순서·개수 어긋남, 연산 값 범위 초과)와 최적화되지 않은 구조(면적뿐 아니라 지연·처리율, 전력·클럭 게이팅 관점 포함)를 정적으로 찾아 사이클 표로 입증하는 것이다.
- **분석은 주석을 지운 사본(`reports/.nocomment/`)으로 한다.** 코드 주석은 읽지 않고 근거로도 쓰지 않는다. 합성에 영향을 주는 pragma 주석(`synopsys`, `synthesis`, `translate_off` 등)은 사본에 남겨 반영한다. 줄 번호는 원본과 같고, `파일:라인`은 원본 경로로 쓴다. 스펙도 `<!-- -->` 주석을 지운 사본으로 읽는다.
- 분석은 매번 지정한 소스 폴더와 top 기준 전체 분석이다. 이전 분석과 비교하는 증분 분석은 하지 않는다. 같은 세션에서 다시 분석할 때도 앞 분석의 작업 노트·결과·결론을 쓰지 않고 처음부터 다시 분석한다 (`verilog-review` 2장).
- 분석 결과는 `reports/<top>_review_<YYYYMMDD>.md` 하나만 만든다. 같은 날 다시 분석하면 `_2`, `_3`을 붙이고 덮어쓰지 않는다.
- 이슈는 `V-001` 번호, 심각도 상/중/하, 증상이 드러나는 짧은 제목, 대표 코드 위치로 정리한다. 분류 코드와 확신도는 쓰지 않는다.
- 보고서는 `verilog-report` skill로 만든다 (`reports/pdf/<top>_report_<YYYYMMDD>.pdf`). 박스 제목(`<TOP 대문자> RTL Analysis Report`) → 분석 개요 표(TOP·소스 폴더, 블록 기능, 이슈 수, 블랙박스, 그레이박스, 분석 소스 파일·줄 수, 참고 스펙, 분석시간·룰 버전, 사용모델·노력, 소요시간·토큰 사용량) → 설계 구조 그림(die layout) → 요약 표 → 이슈별 상세 → 점검 커버리지 → 블랙박스 확인 사항 → 부록(점검 ID·심각도 기준) 순서로, 빈 페이지 없이 이어서 작성한다. 직접 실행: `/verilog-report`
