# verilog-static-analysis

Claude Code에서 Verilog / SystemVerilog RTL을 **코드만 읽어서** 분석하고, 결과를 PDF 보고서로 만드는 규칙 모음입니다.

- lint나 단순 신호 누락이 아니라, **신호 간 관계와 사이클을 따라가야 보이는 문제**를 찾습니다.
- 시뮬레이터, lint, 합성 도구를 쓰지 않습니다. 찾은 문제는 사이클 표로 입증합니다.
- 결과는 `<TOP> RTL Analysis Report` PDF로 정리합니다.

보고서 예시: [`report_template.pdf`](verilog-project/.claude/skills/verilog-report/assets/report_template.pdf)

현재 룰 버전: **v0.8.11**

## 무엇을 찾나

| 종류 | 예 |
|------|----|
| 출력 결과 이상 | 데이터 깨짐, 정렬 어긋남, 순서 바뀜, 이전 트랜잭션 값이 섞임, 연산 overflow |
| 멈춤·교착 | 오지 않는 이벤트를 기다림, 서로 기다림, 꺼진 클럭이 다시 안 켜짐 |
| 잘못된 state | 의도하지 않은 전이, 정의되지 않은 인코딩, 복귀 경로 없음 |
| 이벤트 유실·중복 | pulse 놓침, 요청 두 번 처리, CDC 유실, 늦은 백프레셔로 버퍼 넘침 |
| 리셋 의존 오동작 | 리셋 해제 직후 가짜 이벤트, 리셋 없는 값이 제어에 섞임 |
| 최적화되지 않은 구조 | 쉬는 사이클, 중복 연산, 과한 비트폭, 긴 조합 경로, load enable 누락으로 인한 전력 낭비 |

점검은 모듈 안 15개(M1~M15)와 모듈 간 4개(X1~X4)로 나뉘고, 매번 같은 순서로 전부 확인합니다. 어떤 모듈의 어떤 점검에서 이슈가 나왔는지는 보고서의 "점검 커버리지" 표에 남습니다.

## 준비

1. [Claude Code](https://claude.com/claude-code)를 설치합니다.
2. 이 저장소의 `verilog-project/` 폴더를 통째로 복사해 작업 폴더로 씁니다. 이미 있는 프로젝트에 넣으려면 `verilog-project/` 안의 `CLAUDE.md`와 `.claude/`를 그 프로젝트 폴더에 복사합니다.
3. PDF 보고서까지 만들려면 **pandoc**과 **xelatex**(MiKTeX 또는 TeX Live)가 필요합니다. 없으면 보고서를 만들 때 설치할지, Markdown 보고서로 마칠지 묻습니다. 글꼴은 저장소에 들어 있어 따로 설치하지 않습니다.
4. 소요시간·토큰 사용량 측정에 **python**을 씁니다. 없으면 그 칸만 "측정 불가"로 나오고 분석은 그대로 진행됩니다.

Windows에서는 Git Bash가 있어야 합니다 (Git for Windows에 들어 있습니다).

## 폴더 구성

```
verilog-project/
  CLAUDE.md              세션 규칙 (분석 범위, 시작 절차, 룰 버전)
  .claude/skills/
    verilog-review/      분석 절차와 점검 항목
    verilog-report/      PDF 보고서 형식, 변환 스크립트, 글꼴
  source/                분석할 Verilog 소스 (직접 만듭니다)
    graybox/             신호 흐름만 보고 자체 문제는 분석하지 않을 모듈
  docs/
    analysis-spec.md     분석용 스펙 (선택, 직접 만듭니다)
    example/             스펙 작성 예시
  reports/               분석 결과와 보고서 (자동으로 만들어집니다)
```

| 구분 | 넣는 곳 | 분석 방식 |
|------|---------|-----------|
| 분석 대상 | `source/` | 모든 점검을 적용합니다 |
| 그레이박스 | `source/graybox/` | 코드를 읽어 다른 모듈의 신호 흐름을 판단하는 근거로만 씁니다. 검증된 IP나 다른 팀 모듈에 씁니다 |
| 블랙박스 | 넣지 않음 | 소스 폴더에 정의가 없는 모듈은 자동으로 블랙박스가 됩니다. 문제가 없으려면 만족해야 할 조건을 보고서에 적습니다 |

## 사용 방법

### 1. 소스를 넣고 Claude Code를 실행합니다

`source/`에 `.v`, `.sv`, `.vh`, `.svh` 파일을 넣고, 작업 폴더에서 Claude Code를 실행합니다. 아무 말이나 입력하면 안내 박스가 나옵니다.

### 2. top 모듈을 알려주고 분석을 시작합니다

```
top은 uart_top으로 분석을 시작해줘
```

소스 폴더가 `source`가 아니면 같이 알려줍니다.

```
소스 폴더는 rtl/uart, top은 uart_top으로 분석을 시작해줘
```

### 3. 분석 구성을 확인합니다

분석을 시작하기 전에 모듈을 훑어 구성 표를 보여줍니다. 분석 / 그레이박스 / 블랙박스 / 미사용 모듈과 참고할 스펙 파일이 맞는지 확인하고 답합니다.

```
위 구성이 맞나요? 맞으면 다음으로 넘어갑니다.
```

구성이 다르면 파일을 옮기거나 추가한 뒤 다시 확인해 달라고 하면 됩니다.

### 4. PDF 보고서를 만들지 고릅니다

```
분석을 마친 뒤 PDF 보고서(/verilog-report)까지 한 번에 만들까요?
1. 분석 + PDF 보고서
2. 분석만 (보고서는 나중에 요청)
```

처음부터 `top은 uart_top으로 분석하고 PDF 보고서까지 만들어줘`라고 요청하면 이 질문은 나오지 않습니다.

### 5. 결과를 확인합니다

| 파일 | 내용 |
|------|------|
| `reports/<top>_review_<날짜>.md` | 분석 결과 |
| `reports/pdf/<top>_report_<날짜>.pdf` | PDF 보고서 |

같은 날 다시 분석하면 `_2`, `_3`이 붙고 이전 파일은 덮어쓰지 않습니다. 보고서만 나중에 만들려면 이렇게 요청합니다.

```
verilog-report로 PDF 보고서 만들어줘
```

세션 중 언제든 `버전`이나 `사용법`이라고 물으면 룰 버전과 사용법 요약을 보여줍니다.

## 보고서 읽는 법

보고서는 아래 순서로 구성됩니다.

1. **분석 개요**: top, 블록 기능, 이슈 수, 블랙박스·그레이박스, 분석한 소스 규모, 룰 버전, 사용 모델, 소요시간, 토큰 사용량
2. **설계 구조**: 인스턴스 계층을 블록 종류별 색으로 그린 그림
3. **요약**: 이슈 번호(`V-001`), 심각도, 한 줄 제목, 코드 위치
4. **상세**: 이슈마다 심각도 근거, 요약, 발생 가능한 문제, 문제 설명, 신호 흐름, 발생 조건, 사이클 표, 수정 제안(diff)
5. **점검 커버리지**: 모듈 × 점검 항목 표. `OK`는 확인했고 문제 없음, `-`는 해당 없음, `V-00n`은 이슈
6. **블랙박스 확인 사항**: 블랙박스가 만족해야 할 조건
7. **부록**: 점검 ID와 심각도 기준

심각도는 세 단계입니다.

| 심각도 | 뜻 |
|:--:|------|
| 상 | 정상 입력에서 잘못된 데이터가 나가거나, 리셋 없이는 빠져나올 수 없는 멈춤 |
| 중 | 특정 조건에서만 생기는 오동작, 리셋으로 복구되는 멈춤, 효과가 큰 최적화 |
| 하 | 현재 조건에서는 생기지 않는 가정 위반, 면적·전력의 작은 최적화 |

## 스펙을 주면 더 정확해집니다

스펙이 없으면 프로토콜이 허용하는 모든 입력 순서와 타이밍을 가정합니다. 실제로는 오지 않는 입력 때문에 이슈가 나오는 것을 줄이려면 `docs/analysis-spec.md`를 만들어 주세요. 형식은 [`docs/example/analysis-spec.md`](verilog-project/docs/example/analysis-spec.md)를 참고합니다.

```markdown
# 분석 스펙

## 입력 조건
- start 는 1클럭 pulse 이고, 이전 작업의 done 이 나온 뒤에만 다시 온다
- cfg_len 은 start 전에 설정되고, 작업 중에는 바뀌지 않는다

## 출력 조건
- 받는 쪽은 m_axis_tready 를 최대 16클럭까지 0 으로 둘 수 있다

## 요청 사항
- 작업 중 srst 가 오면 다음 start 부터 정상 동작하는지 확인
```

- **입력 조건 / 출력 조건**: 여기 적힌 제약을 벗어나는 경우는 이슈로 올리지 않습니다.
- **의도된 동작**: 적어 두면 그 동작 자체는 이슈로 올리지 않습니다.
- **성능 목표 / 전력 목표**: 최적화 이슈를 판단하는 기준이 됩니다.
- **요청 사항**: 반드시 확인하고, 항목마다 결과를 한 줄씩 알려줍니다.

`docs/example/` 안의 파일은 작성 예시라서 분석에 쓰지 않습니다.

## 알아둘 점

- **정적 분석입니다.** 코드를 읽고 추론한 결과이므로, 올라온 이슈는 시뮬레이션이나 리뷰로 확인하고 반영하세요. 이슈가 없다고 해서 설계에 문제가 없다는 뜻은 아닙니다.
- **실행마다 결과가 조금 다를 수 있습니다.** 같은 소스라도 모델과 실행에 따라 찾는 이슈가 달라질 수 있습니다. 중요한 블록은 두 번 이상 돌려 보는 것을 권합니다.
- **소스를 고치지 않습니다.** 수정은 보고서에 diff로만 제안합니다. 소스 폴더 안에 파일을 만들거나 옮기지도 않습니다.
- **매번 전체를 분석합니다.** 이전 결과와 비교하는 증분 분석은 하지 않습니다.
- **수정 후 재분석은 새 세션에서 하세요.** 소스를 고친 뒤 같은 세션에서 다시 분석하면 앞 분석 내용에 끌려 새 문제를 놓치기 쉽습니다. `/clear`로 새 세션을 시작한 뒤 분석을 요청합니다.
- 응답과 보고서는 한국어로 작성됩니다.
